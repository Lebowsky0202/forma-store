# Архитектура FORMA

## Границы

Frontend — React SPA, сервер — Express REST API, база — PostgreSQL с Prisma. Клиент обращается к одному origin: Vite проксирует `/api` и `/uploads` локально, Nginx — в Docker. Backend и PostgreSQL не публикуют порты наружу в Compose. Backend работает от непривилегированного пользователя. Для публичного запуска необходим HTTPS reverse proxy.

Витрина и админ-панель используют общий типизированный клиент API. TanStack Query хранит данные сервера; Zustand хранит текущую сессию и гостевые корзину/избранное. Access JWT находится в памяти; refresh token — в HttpOnly cookie. После входа гостевые позиции переносятся в серверную корзину с повторной проверкой наличия. Не перенесённые позиции не теряются в локальном состоянии.

## Деньги и склад

Все цены — целые тенге. При чтении корзины цены берутся из текущего каталога. При оформлении сервер сам вычисляет сумму, проверяет активность товаров и доставки, условно уменьшает остаток (`stock >= quantity`) и создаёт снимки позиций заказа. Всё выполняется в SERIALIZABLE-транзакции с ограниченными повторениями конфликта сериализации. Неудача любой позиции откатывает весь заказ.

Пара `(userId, idempotencyKey)` уникальна; повтор того же запроса возвращает прежний заказ. Ключ с другим содержимым вызывает конфликт. Заказ хранит название, артикул, размер, цвет, изображение и цену, поэтому последующее редактирование товара не меняет историю покупки.

Отмена разрешена по графу переходов, а возврат остатков выполняется только при фактической смене статуса на CANCELLED в той же транзакции. Повторная отмена не увеличивает склад снова. Использованные варианты архивируются, сохраняя связи с историей заказов.

## Оплата

Поддерживается COD — оплата при получении. Создание заказа создаёт Payment со статусом PENDING и не списывает деньги. Подтверждение администратором PAID или DELIVERED фиксирует получение оплаты. Автоматического возврата денег нет: при отмене уже оплаченного заказа история платежа сохраняется, возврат проводится продавцом отдельно. Интерфейс не имитирует банковский платёж. Подключение эквайринга потребует учётной записи провайдера, ключей и обработки подписанных webhook.

## Защита

- bcrypt, JWT HS256 с ограничением алгоритма, issuer/audience и сроком жизни.
- Случайные refresh tokens; в БД хранится SHA-256, ротация токенов и отзыв семейства при повторном использовании.
- Текущий статус пользователя, роль и версия сессий проверяются по БД; изменение роли/активности отзывает сессии.
- Проверка владельца для корзины, адресов и заказов; каждый административный endpoint защищён ролью.
- Zod-валидация, ограничение количества/размера запросов, пагинация, CORS и Origin, rate limiting, Helmet.
- Загрузка только администратором; лимит 5 МБ, распознавание и перекодирование изображений, случайные имена. SVG и исполняемые файлы не принимаются.
- Секреты генерируются локально и исключены из Git. Seed не содержит паролей по умолчанию.

## Масштабирование

API не хранит корзины/заказы в памяти процесса. Для нескольких экземпляров нужно вынести ограничение частоты запросов в общее хранилище и перенести uploads в объектное хранилище либо общий диск. PostgreSQL требует резервного копирования и мониторинга; изображения каталога и юридические/контактные сведения должны быть заменены реальными данными продавца перед публичным запуском.
